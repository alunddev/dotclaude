# Message queue patterns

The patterns are universal — what changes between brokers is the API. Get the patterns right and switching brokers is mechanical.

## When to use this skill

- Designing async communication between services
- Decoupling a slow operation from the request path
- Implementing retries with backoff
- Debugging duplicate processing, lost messages, or out-of-order delivery
- Choosing between Kafka, RabbitMQ, SQS, NATS, Redis Streams

## Core concepts

### Delivery guarantees (you must pick)

- **At-most-once**: fire and forget. Messages may be lost. Acceptable for non-critical telemetry.
- **At-least-once**: delivered ≥ 1 time. **Consumer must be idempotent.** This is the default for serious systems.
- **Exactly-once**: a marketing term. Achievable with effort (idempotency + dedup), not "for free" from the broker.

**Reality**: design for at-least-once + idempotent consumers. Don't trust "exactly-once" marketing.

### Push vs. pull

- **Push** (RabbitMQ classic, NATS): broker sends to consumer. Easier; harder to backpressure.
- **Pull** (Kafka, SQS, Redis Streams): consumer asks for next batch. Better backpressure; consumer manages position.

Most modern systems lean pull.

## Pattern 1: Idempotent consumer (MANDATORY for at-least-once)

Every consumer of an at-least-once queue MUST be idempotent. Always.

```python
# Bad — duplicates create double-charges
def charge(msg):
    charge_card(msg.user_id, msg.amount)

# Good — idempotent via business key
def charge(msg):
    if charges_repo.exists(idempotency_key=msg.idempotency_key):
        return  # already processed
    with transaction():
        charge_card(msg.user_id, msg.amount)
        charges_repo.insert(idempotency_key=msg.idempotency_key, ...)
```

The idempotency key must come from the **producer**, not be generated by the consumer.

## Pattern 2: Dead-letter queue (DLQ)

After N failed attempts, send the message to a DLQ for human inspection.

```python
def handle(msg):
    try:
        process(msg)
        ack(msg)
    except RetryableError:
        if msg.attempts >= MAX_RETRIES:
            dlq.send(msg, reason="max_retries", error=current_exc())
            ack(msg)  # remove from main queue
        else:
            nack(msg, requeue=True, delay=backoff(msg.attempts))
    except FatalError as e:
        # Don't retry malformed messages
        dlq.send(msg, reason="fatal", error=str(e))
        ack(msg)
```

DLQ rules:
- Alert when it's non-empty.
- Have a runbook for triaging it.
- Build a UI to reprocess after fix (or a CLI script).
- Never silently drop DLQ contents on a schedule.

## Pattern 3: Exponential backoff with jitter

```python
import random

def backoff(attempt, base_ms=100, max_ms=30_000):
    exp = min(max_ms, base_ms * (2 ** attempt))
    return random.uniform(0, exp)  # full jitter
```

**Full jitter** (random 0..exp) > **decorrelated jitter** > **equal jitter** > **no jitter**.
Never retry without jitter when many consumers share a queue — they'll synchronize and DDoS your downstream.

## Pattern 4: Outbox pattern (transactional publish)

Problem: you update the DB AND publish a message. If one succeeds and the other doesn't, state diverges.

Solution: write the message to an `outbox` table in the same DB transaction, then a separate publisher reads the outbox and publishes.

```sql
BEGIN;
  INSERT INTO orders (...) VALUES (...);
  INSERT INTO outbox (topic, payload, created_at) VALUES ('order.created', '...', now());
COMMIT;
```

A worker polls `outbox`, publishes to the broker, marks the row sent. **Atomic from the app's view, eventual from the broker's view.**

## Pattern 5: Inbox pattern (deduplication at consumer)

Consumer side mirror of outbox: record received message IDs in an `inbox` table; skip if already seen.

```sql
BEGIN;
  -- Check inbox first
  INSERT INTO inbox (message_id, processed_at) VALUES ('msg-123', now())
  ON CONFLICT (message_id) DO NOTHING
  RETURNING message_id;
  -- If RETURNING is empty → already processed, exit.
  -- Otherwise, do the work.
  ...
COMMIT;
```

## Pattern 6: Fan-out (one producer, many consumers)

- **RabbitMQ**: fanout exchange → multiple queues
- **Kafka**: one topic, multiple consumer groups (each group reads independently)
- **SQS**: SNS topic → multiple SQS queues
- **Redis Streams**: consumer groups via `XREADGROUP`

Use case: order placed → notify warehouse + email service + analytics, each independently.

## Pattern 7: Saga (long-running distributed transactions)

When a "transaction" spans 3+ services, distributed transactions are impractical. Use a saga: each step has a compensating action.

```
Order saga:
  1. Reserve inventory       → compensate: release inventory
  2. Charge payment          → compensate: refund payment
  3. Schedule shipment       → compensate: cancel shipment

If step 3 fails → run compensations 2 and 1.
```

Two flavors:
- **Choreography**: each service publishes events, others react. Decentralized.
- **Orchestration**: a central saga coordinator drives the flow. Centralized.

Orchestration is easier to reason about; choreography scales better.

## Pattern 8: Bulkhead

Don't let one consumer's slowness starve others. Run separate consumer pools per priority/queue:

- High-priority queue: 8 workers
- Normal queue: 16 workers
- Bulk/background queue: 4 workers

Slow batch jobs can't block latency-sensitive work.

## Broker selection

| Need | Pick |
|---|---|
| High-throughput event streaming, replay | **Kafka** (or Redpanda) |
| Classic work queue, complex routing | **RabbitMQ** |
| AWS-native, simple, managed | **SQS** |
| Lightweight, in-cluster, simple | **NATS** |
| Already have Redis, low scale | **Redis Streams** |
| Real-time pub/sub over WebSockets | **NATS / Centrifugo / Pusher** |

## Ordering guarantees

- **Kafka**: ordered within a partition. Order across partitions is undefined. Pick partition key carefully.
- **RabbitMQ**: ordered within a queue with a single consumer. Concurrent consumers break order.
- **SQS FIFO**: ordered within a `MessageGroupId`. Throughput limits apply.
- **NATS JetStream**: ordered within a subject.

**Rule**: if you need ordering, partition by the entity (user_id, order_id) so all related messages land in the same partition.

## Anti-patterns

- **Treating queues as RPC.** Queues are async. If you need a response, use HTTP/gRPC or implement request/reply with a correlation_id (which is rare and complex).
- **Storing huge payloads in messages.** Keep them small. For large data, send a pointer (S3 URL) and have the consumer fetch.
- **Sharing one queue across unrelated message types.** Split queues by use case so you can scale and DLQ separately.
- **No timeout on consumers.** A stuck consumer holds the message lease forever. Set visibility timeouts / processing deadlines.
- **Skipping idempotency "because retries are rare".** They happen. Network blip, deploy, broker reconnect. Always idempotent.
- **Ignoring the DLQ.** A DLQ filling up silently is worse than no DLQ.
- **Publishing without context.** Always include: message_id, correlation_id, timestamp, schema_version. Future-you will thank you.

## Schema evolution

Messages outlive code. Plan for it:

- **Use a schema registry** (Confluent, AWS Glue) for Kafka.
- **Version your message types** explicitly in the payload: `{"version": 2, "data": {...}}`.
- **Additive changes only** when possible — add fields, never remove or rename.
- **Make consumers tolerant** of unknown fields (default behavior in Protobuf, opt-in in JSON).

## Monitoring (what to alert on)

- **Queue depth** rising consistently → consumers can't keep up
- **DLQ non-empty** → manual triage needed
- **Consumer lag** (Kafka) → behind by N messages or N seconds
- **Message age** (oldest message in queue) → starvation indicator
- **Publish/consume rate mismatch** → producer outpacing consumer

Dashboards for each. Alerts only on actionable thresholds.
