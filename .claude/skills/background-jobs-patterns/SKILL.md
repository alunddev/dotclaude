# Background jobs patterns

The request path should be fast. Anything that takes > 200ms and doesn't need to return a value to the user belongs in a background job.

## When to use this skill

- Moving slow operations off the request path (sending email, generating reports, encoding video)
- Scheduling periodic work (nightly cleanup, hourly reports)
- Implementing retry logic for flaky external services
- Debugging stuck, duplicate, or lost jobs
- Choosing a job framework

## When to use a job vs. a queue (subtle)

- **Job framework** (Celery, Sidekiq, BullMQ, Asynq): higher-level. Function call → automatic enqueue, retry, monitor. Good for app-internal async work.
- **Raw message queue** (Kafka, SQS): lower-level. For cross-service events. See `message-queue-patterns`.

If both producer and consumer are your code and live in the same repo, use a job framework. If they're separate services, use a queue.

## Core principles

1. **Jobs are idempotent.** They may run twice. Always.
2. **Jobs have timeouts.** Stuck jobs don't block forever.
3. **Jobs are observable.** You can see what's running, what failed, why.
4. **Failed jobs go to a DLQ.** Don't drop them silently.
5. **Shutdown is graceful.** SIGTERM = finish in-flight, don't accept new.

## Pattern 1: Idempotent execution

Every job MUST be safe to run multiple times. Test this — re-run the job; the second time should be a no-op.

```typescript
// BullMQ example
worker.on('completed', async (job) => {
  // job framework already records completion
});

async function sendOrderConfirmation(job) {
  const { orderId, idempotencyKey } = job.data;

  // Check if already done
  const sent = await db.notifications.findOne({ idempotencyKey });
  if (sent) return { status: 'already_sent' };

  await emailService.send(orderId);
  await db.notifications.insert({ idempotencyKey, sentAt: new Date() });
}
```

The idempotency key is generated by the producer, not by the worker. The producer assigns it once.

## Pattern 2: Retries with exponential backoff + jitter

Most frameworks have this built in; configure it correctly:

```typescript
// BullMQ
await queue.add('process-payment', data, {
  attempts: 5,
  backoff: { type: 'exponential', delay: 1000 }, // 1s, 2s, 4s, 8s, 16s
});
```

```python
# Celery
@app.task(
    autoretry_for=(RequestException,),
    retry_backoff=True,
    retry_backoff_max=60,
    retry_jitter=True,
    max_retries=5,
)
def call_external_api(payload):
    ...
```

Rules:
- Retry only **retryable** errors (network, 5xx, timeouts). Not validation errors, not 4xx.
- Cap max retries (5–10 usually). Then DLQ.
- Add jitter — without it, retries synchronize and stampede.

## Pattern 3: Dead-letter queue

After max retries, send to DLQ for manual triage:

```python
@app.task(bind=True, max_retries=5)
def process(self, payload):
    try:
        do_work(payload)
    except RetryableError as e:
        try:
            self.retry(countdown=backoff(self.request.retries))
        except MaxRetriesExceededError:
            dlq.send({
                'payload': payload,
                'error': str(e),
                'attempts': self.request.retries,
                'failed_at': datetime.utcnow().isoformat(),
            })
```

DLQ rules:
- Alert on DLQ growth (Prometheus, PagerDuty).
- Have a CLI / admin UI to inspect + reprocess.
- Never auto-drop DLQ items.
- Code review every DLQ-handling change.

## Pattern 4: Job timeouts

Every job has a max runtime. No exceptions.

```typescript
// BullMQ
await queue.add('encode-video', data, {
  attempts: 3,
  timeout: 5 * 60 * 1000, // 5 minutes
});
```

```python
# Celery
@app.task(time_limit=300, soft_time_limit=270)
def encode_video(video_id):
    try:
        encode(video_id)
    except SoftTimeLimitExceeded:
        cleanup_partial_work()
        raise
```

Soft limit → cleanup time. Hard limit → kill.

## Pattern 5: Priority queues / bulkheads

Don't let slow batch work starve latency-sensitive jobs:

```python
# Separate queues by priority
@app.task(queue='high')
def send_password_reset(user_id): ...

@app.task(queue='normal')
def send_marketing_email(user_id): ...

@app.task(queue='bulk')
def reindex_all_documents(): ...

# Workers per queue
# celery -A app worker -Q high --concurrency=8
# celery -A app worker -Q normal --concurrency=16
# celery -A app worker -Q bulk --concurrency=4
```

Or in BullMQ:

```typescript
const highPriorityQueue = new Queue('high', { connection });
const lowPriorityQueue = new Queue('low', { connection });

new Worker('high', handler, { connection, concurrency: 8 });
new Worker('low', handler, { connection, concurrency: 4 });
```

## Pattern 6: Scheduled / recurring jobs

```typescript
// BullMQ repeatable
await queue.add('nightly-cleanup', {}, {
  repeat: { pattern: '0 2 * * *' }, // 2 AM daily
  jobId: 'nightly-cleanup-singleton', // avoid duplicates
});
```

```python
# Celery beat
app.conf.beat_schedule = {
    'nightly-cleanup': {
        'task': 'tasks.cleanup',
        'schedule': crontab(hour=2, minute=0),
    },
}
```

Rules for scheduled jobs:
- **Lock to prevent overlapping runs** — if the previous run is still going, skip this one or queue it.
- **Idempotent over partial completion** — if the job dies halfway, the next run should pick up where it left off (or redo safely).
- **Bounded execution time** — a "nightly" job shouldn't run for 12 hours.

### Distributed lock for singletons

```python
def with_lock(lock_name, ttl=3600):
    def wrapper(fn):
        def inner(*args, **kwargs):
            lock = redis.set(f"lock:{lock_name}", "1", nx=True, ex=ttl)
            if not lock:
                logger.info(f"skipped {lock_name}: another instance running")
                return
            try:
                return fn(*args, **kwargs)
            finally:
                redis.delete(f"lock:{lock_name}")
        return inner
    return wrapper

@app.task
@with_lock("nightly-cleanup")
def cleanup():
    ...
```

## Pattern 7: Chunked / batched processing

Big jobs run forever; chunked jobs are observable and resumable.

```typescript
// Bad: one job processes 1M users
async function reprocessAllUsers() {
  const users = await db.users.findAll(); // 1M rows
  for (const u of users) { process(u); }
}

// Good: orchestrator + chunks
async function reprocessAllUsers() {
  const total = await db.users.count();
  const chunkSize = 1000;
  for (let offset = 0; offset < total; offset += chunkSize) {
    await queue.add('reprocess-chunk', { offset, limit: chunkSize });
  }
}

async function reprocessChunk(job) {
  const users = await db.users.findAll({ offset: job.data.offset, limit: job.data.limit });
  for (const u of users) await process(u);
}
```

Benefits: parallelizable, resumable, observable per chunk.

## Pattern 8: Graceful shutdown

```typescript
// BullMQ
process.on('SIGTERM', async () => {
  console.log('shutting down...');
  await worker.close();   // wait for current job, refuse new
  await redis.quit();
  process.exit(0);
});
```

```python
# Celery — handled by framework if you don't kill -9
# Default: workers finish in-flight on SIGTERM
# In containers: set `terminationGracePeriodSeconds: 60+` in k8s
```

K8s manifest:
```yaml
terminationGracePeriodSeconds: 60  # ≥ max expected job runtime
```

## Pattern 9: Observability

Every job emits structured logs and metrics:

```python
logger.info("job.started", extra={"job_id": id, "queue": "high", "name": "process_order"})
# ... work ...
logger.info("job.completed", extra={"job_id": id, "duration_ms": elapsed, "result": result})
```

Metrics (Prometheus / equivalent):
- `jobs_enqueued_total{queue, name}`
- `jobs_completed_total{queue, name, status}` (status: success/retry/dlq)
- `jobs_duration_seconds{queue, name}` (histogram)
- `queue_depth{queue}` (gauge — scrape from broker)

Alerts:
- DLQ size > threshold
- Job duration p99 > 2× baseline
- Queue depth growing unboundedly

## Pattern 10: Workflow / saga jobs

Multi-step jobs with compensations. See `message-queue-patterns` saga section. Frameworks: Temporal, Azure Durable Functions, AWS Step Functions, Celery canvas.

For complex orchestration (>3 steps, retries per step, branching), use a workflow engine — not raw jobs.

## Framework selection

| Framework | Lang | Notes |
|---|---|---|
| **BullMQ** | Node.js | Redis-backed, modern, great DX |
| **Bull** | Node.js | Older BullMQ; use BullMQ for new projects |
| **Celery** | Python | Battle-tested, Redis or RabbitMQ |
| **Dramatiq** | Python | Simpler Celery alternative, fewer footguns |
| **RQ** | Python | Simplest, Redis-only, no scheduler |
| **Sidekiq** | Ruby | The gold standard for Ruby |
| **Asynq** | Go | Redis-backed, Sidekiq-inspired |
| **Solid Queue** | Rails 8+ | DB-backed (no Redis needed) |
| **Hangfire** | .NET | DB-backed, has UI |
| **Temporal** | Polyglot | Durable workflows, learning curve |

Pick the most boring one that fits.

## Anti-patterns

- **Doing the slow thing in the request path** "because it's only 500ms" — that's 5× too slow.
- **No retries** — first network hiccup loses data.
- **Infinite retries** — fills the queue, never DLQs.
- **No timeout** — one stuck job clogs a worker forever.
- **Catching all exceptions in workers** — silent failures, no metrics.
- **Sharing one queue for everything** — can't prioritize, can't isolate.
- **Running scheduled jobs without locks** — overlap = double processing.
- **Storing huge payloads in jobs** — pass IDs and let the worker fetch.
- **`time.sleep()` in workers** to "wait" — uses up worker capacity. Use scheduled retry instead.
- **Updating the DB from many parallel workers without locks** — race conditions and lost updates.
